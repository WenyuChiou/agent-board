# Contributing

Read [AGENTS.md](AGENTS.md) for code layout and conventions. Keep changes scoped, use synthetic data, and report checks and limitations in the PR.

## Outside contributors

You are welcome, whether you work by hand or with an AI. You are a contributor ([Roles](#roles)). Rules below that mention lanes, dot, Muse, Codex slots or the maintainer session are for the owner's own agents; [docs/CONTRIBUTOR-PATH.md](docs/CONTRIBUTOR-PATH.md) gives every step you need.

- **Bugs and ideas:** the Bug report and Idea forms, with made-up data.
- **Small docs fixes:** a `docs:` pull request that changes only `README*.md` or `docs/**/*.md` (not `docs/FORMAT.md` or `docs/dev/`), at most three files and 50 added lines, needs no issue and no claim.
- **Planned work:** an open issue labelled `ready` and `for-agent`, not `blocked` or `claimed`. Claim it from your own GitHub account (rule 3). Up to two open pull requests at a time.
- **Ask first** on the issue before changing `AGENTS.md`, `CONTRIBUTING.md`, `.github/`, `package.json` or `.claude-plugin/`, adding a dependency, or sending more than about 500 lines.
- **Report only what you ran.** Paste the output of `node scripts/preflight.mjs`; the reviewer reruns the checks.
- **Checks wait for approval.** GitHub holds the checks on a fork's pull request until a collaborator with write access, the maintainer or the owner approves the run after reading the diff ([team-process](docs/dev/team-process.md#pull-requests-from-forks)).

## Roles

Large projects split who may do what into a short ladder: GitHub's repository roles, Node.js Collaborators, Kubernetes reviewers and approvers, Apache committers. This repository keeps four roles. Anyone may contribute; a review that counts toward a merge, and the merge itself, come from people the owner trusts with write access.

| | Contributor | Collaborator | Maintainer | Owner |
|---|---|---|---|---|
| Who | a person without write access, by hand or with an AI, and that person's agents; usually from a fork | a person the owner has given write access, and that person's agents | the Claude Code session the owner names | the repository owner |
| Issues | opens issues; claims an issue labelled `ready` and `for-agent` from their own login (rule 3) | also triages: labels, milestones, `ready`, `blocked` | triages and plans the milestones | decides `needs-owner` questions |
| Pull requests | opens them from a fork; at most two open (rule 10) | pushes branches to this repository | same as a collaborator | same as a collaborator |
| Review | may review and comment; the verdict is advice and does not count toward a merge | posts the `Review:` verdict that counts, on pull requests by another author, excluding the author's own agent, lane or subagent (rules 8 and 9); a collaborator the owner names here (now SUPERD6) has the maintainer's exception for its own pull requests, except governance, workflow and release pull requests | same; a code-review subagent it runs may approve its own pull requests under rule 8's conditions | same as a collaborator |
| Merge | no | merges once rule 9 holds; GitHub deletes eligible same-repository branches, and a fork owner may need to delete their branch | same as a collaborator | same as a collaborator |
| CI on forks | no | approves a held run after reading the diff ([team-process](docs/dev/team-process.md#pull-requests-from-forks)) | same as a collaborator | same as a collaborator |
| Governance files and workflows | asks first on the issue | changes them only with the owner's approval of the content (rule 12) | same as a collaborator | approves the content |
| Releases | may comment on or review a release pull request as advice | may review a release pull request under rule 8 | prepares and merges the release pull request, tags the release and makes the GitHub release | authorizes releases and publishes to npm |
| Settings and access | no | no | no | repository settings, and who has write access |

The owner invites a contributor to become a collaborator once their pull requests have merged and they have followed these rules; there is no fixed count. The owner also removes write access.

## Set up

Clone the repository and use Node 22.18+ or 24 for the tests (the installed bundle supports Node 18+). Use Bun 1.4.2 when rebuilding generated files. `package.json` is only the npm package's manifest: it has no dependencies and no scripts, so there is nothing to install.

Independent development and installation do not require Claude Code. Optional pane validation uses Claude Code 2.1.301 in CI, pinned in `.github/workflows/test.yml`; `plugin validate` and `plugin test` are offline and need no model login.

## Run the checks

From the repository root, with Node 22.18+ or 24 and npm (for `npx`), the check catalog below; CI selects the affected groups for each pull-request push:

```sh
node --test tests/exchange.test.mjs tests/messaging.test.mjs tests/pr-check.test.mjs tests/preflight.test.mjs tests/changelog-fold.test.mjs tests/team-stats.test.mjs
node --test tests/board.test.mjs tests/board-storage.test.mjs tests/codex-local.test.mjs tests/local-lock.test.mjs tests/prompt-hooks.test.mjs tests/codex-host.test.mjs tests/codex-fallback.test.mjs tests/legacy-connect.test.mjs tests/connect-worker.test.mjs
node --test tests/npm-package.test.mjs
npx --yes bun@1.4.2 scripts/build-board.ts --check
npx --yes bun@1.4.2 scripts/build-released.ts --check
node scripts/pr-check.mjs --pr <N>
```

These lists are the ones in `.github/workflows/test.yml`; if they ever differ, the workflow is right. Fetch release tags (`git fetch --tags origin`) before the released-files check. Rebuild changed bundle sources with `npx --yes bun@1.4.2 scripts/build-board.ts`; never hand-edit `hooks/board-script.ts`. `pr-check.mjs` says what a pull request still lacks under [Pull requests](#pull-requests); before opening one, run it with `--body-file <file> --title "<title>"`.

For the optional plugin and legacy installers:

```sh
claude plugin validate --strict .
claude plugin test .
bash tests/setup.check.sh
powershell -NoProfile -ExecutionPolicy Bypass -File tests/setup.check.ps1
python3 -B scripts/remote-reporter/test_pipeline.py
```

`claude` comes from npm (`npm install -g @anthropic-ai/claude-code@2.1.301`, the version CI pins); `plugin validate` and `plugin test` are offline and need no login. Run the installer check matching the changed script/OS; each uses temporary fixtures. Windows CI uses `python` for the stdlib reporter tests. None of these checks sends model prompts.

Run strict TypeScript for changed standalone modules with Node typings from your development environment. Full `tsc -p .` additionally needs the host-generated `.claude-plugin/types/` SDK, written when Claude Code loads the local plugin (`claude --plugin-dir .`). It is gitignored and must not be invented or edited. If unavailable, report full typechecking as unrun; passing standalone checks does not replace it. Do not start model work merely to claim an offline check passed.

CI selects affected groups from changed paths and base/head dependencies, using the same plan for Draft and Ready. On a pull request, Node groups run Node 22 on Ubuntu and Node 24 on Windows and plugin runs on Ubuntu, and on Windows too when a change reaches the plugin's runtime (`hooks/`, the bundle, the plugin manifest, `package.json`, `.gitattributes` or the test workflow); `main`, the weekly run, a manual run and release PRs run every pair. Full runs occur for manifests, governance, selector changes, unclassified paths, releases, the weekly schedule and explicit full dispatch. The first selector rollout runs every group. The PR check still runs separately on every pull request. Generated checks run when affected; full `tsc -p .` remains separate. See [affected CI](docs/dev/CI.md).

## Changes and evidence

Put logic in pure `hooks/` modules; engine calls stay in `hooks/register.tsx`. User-visible strings belong in all three tables. Use meaningful behavioral tests for messaging, state, storage and ownership changes. CHANGELOG fragments name their covering tests. Commits and pull requests follow [Pull requests](#pull-requests).

Record progress, native hook execution, UI controls, transport acceptance and actual model ACKs separately. Identify the native host and surface; an owned app-server is not a CLI TTY or a desktop chat. A mock, tagged file or accepted RPC cannot prove live delivery. Never use a normal reply as tool/merge approval. Real model tests require an authorized disposable binding and a bounded prompt budget; stop only your own test processes afterward.

For optional OpenCode SDK/DeepSeek loader checks, use the pinned packages and disposable prefix in the [portable acceptance record](docs/validation/2026-10-19-portable-hosts.md). `scripts/check-host-contracts.mjs --runtime-dir <prefix>` uses the actual packages with synthetic host objects; it is not native model acceptance. Normal installation adds no npm dependencies.

## Pull requests

Several agents (Claude Code sessions, Codex, Antigravity, cloud agents such as dot and Muse, and agents on other computers) work in this repository at the same time. These rules keep their work from overlapping. They apply to every agent and person. [docs/CONTRIBUTOR-PATH.md](docs/CONTRIBUTOR-PATH.md) walks through them with the exact commands; where the two disagree, this section wins. [docs/dev/team-process.md](docs/dev/team-process.md) sets how much work is open at once, when a finding becomes an issue, and how a pull request moves from claim to merge. `node scripts/pr-check.mjs` checks rule 2's issue lines and its three-fix limit on a `fix` title, and rules 6 and 10; the `Author:` line, the template sections and pictures' alt text (rule 7); the branch and title names (rules 4 and 5); that a claim names you and your branch (rule 3, not yet its end time: #303); private data in the body and added docs; and, when you run it yourself, the board bundle (rule 5). For a pull request from outside the team it also checks the caps by GitHub login (rule 10), the claim from the author's own login on a `ready` issue (rule 3) and that the title is not a release, only notes a large change or a change to a governance file, and lets a small docs fix (rule 2) through without an issue line or claim. It runs on your computer and on every pull request; the rest is the reviewer's to check.

1. **Nothing reaches `main` except through a pull request.** Never push to `main`. Never force-push a branch: bring it up to date by merging (rule 4).
2. **One feature, one pull request; bug fixes two or three together.** Start from an issue; open one if none fits. A feature gets one branch and one pull request, even when it spans several issues, unless it is split into steps (below). Bug fixes go two or three to a pull request when several are waiting, never more than three; a lone or urgent fix may go alone. Other small issues (docs, tests, chores) follow the same rule with issues of their own kind. Never put a bug fix in a feature pull request. The body opens with one `Fixes #N` or `Part of #N` line for each issue, one right after the other, and you claim every one of those issues (rule 3). When an issue is split into steps, each step's pull request opens with `Part of #N` and the last one with `Fixes #N`. Anything else you find goes in an issue of its own or a comment on the issue that already has it, not into the same pull request. A release pull request needs no issue and has no `Fixes` line. A small docs fix from outside the team (a `docs:` pull request that changes only `README*.md` or `docs/**/*.md`, not `docs/FORMAT.md` or `docs/dev/`, in at most three files and 50 added lines) needs no issue line, no claim and no changelog fragment.
3. **Find work, then claim it.** Work ready to start carries the label `ready`; `for-agent` means any agent may take it and `for-dot` means dot or Muse. The issue body says who it is planned for (`Executor`), what must pass (`Acceptance tests`) and what must land first (`Blocked by`); the body is the current scope. Leave issues labelled `blocked` alone, and those labelled `claimed` unless the claim has run out (below). Before you branch, check the open pull requests (`gh pr list --state open`) and the issue's comments. To claim, comment on the issue

   `Claim: <agent>, <branch>, until <YYYY-MM-DD HH:MM> UTC`

   at most two days ahead, and add the `claimed` label. If you cannot edit labels, say so in the comment; the maintainer sets them. Renew it with a new `Claim:` comment before it runs out. A claim past its time with no pull request may be taken over after a `Claim taken over: <agent>, <branch>` comment. A claim waiting for a free slot (rule 10) says `waiting for a slot` in place of a time; it runs out 7 days after its comment unless renewed the same way. If someone has an open pull request or a live claim, do not start a competing one: comment on theirs. If an earlier claim turns up after yours, withdraw yours. A contributor from outside the team (not the owner, a member or a collaborator) claims from their own GitHub account on an issue labelled `ready` and `for-agent` and not `blocked`; the PR check fails the pull request when that account's claim is missing or another login held a live claim on the issue first.
4. **Branch from current `main`**, named `<type>/<short-slug>` (`fix/question-ledger-write`). When `main` moves, merge it into your branch (`git fetch origin`, `git merge origin/main`) and push; never rebase a pushed branch. The reviewer may do this merge for you, so run `git pull --ff-only` before you commit again. If `main` moved before the merge, the new head needs a new verdict unless that merge of `main` had no conflicts and added nothing else (rule 9). Without write access to this repository, push the branch to your fork and open the pull request from there: the PR check and CI run on it the same way, though GitHub may hold CI runs from a first-time contributor's fork until a collaborator with write access, the maintainer or the owner approves them.
5. **Commits** use `<type>: <summary>` or `<type>(<scope>): <summary>` (for example `feat`, `fix`, `docs`, `test`, `refactor`, `chore`), with a body that says why. The pull request title uses the same form. Commit regenerated files (`hooks/board-script.ts`, `hooks/released.ts`) together with the source change that needs them.
6. **CHANGELOG.** A fix or feature pull request adds one new file for each issue it names, `changelog.d/<issue>-<slug>.md` (for example `changelog.d/229-changelog-fragments.md`), holding that issue's entry exactly as it will read in the CHANGELOG. The entry's first line is `- **area / topic** · ` followed by one to three plain sentences about what changed for the person using agent-board, ending with its issue (`#N`); format and areas in `changelog.d/README.md`. The next line names its covering tests by their exact titles, each in backticks after `Tests:`; the release fold leaves that line out of `CHANGELOG.md`. A fix or feature pull request that changes only documentation writes `Tests: none (documentation only).` Do not edit `CHANGELOG.md` or another pull request's fragment: only the release pull request ([Releases](#releases)) raises the version and folds the fragments into a dated section. Until 0.24.0 ships, an entry under `## Unreleased` is still accepted.
7. **The pull request body** names its author (`Author: <agent>, <branch>`) and fills in every section of the template: the evidence and the head it is for, each check with its result, each check you did not run with `not run:` and why, and what it leaves out. Pictures are synthetic and their alt text says so. Open it as a draft. When the PR check and CI pass, mark it ready (`gh pr ready <N>`) and comment `Ready for review <full head sha>`. After that, change it only when the reviewer asks: answer each finding in a comment, push the fix, and comment `Ready for review <new head sha>`.
8. **Someone other than the author approves; then a collaborator merges.** Anyone may open issues and pull requests, from this repository or from a fork. Any collaborator the owner has given write access to this repository, the Claude Code session the owner has named maintainer, and the owner may review any pull request and merge it once rule 9 holds ([Roles](#roles)). A contributor's review is welcome advice; the approval that counts comes from one of them, and from someone other than the author: a review by the author's own agent, lane or subagent does not count, except for a pull request written by the maintainer or by a collaborator the owner names in [Roles](#roles): a code-review subagent its author runs may approve it when all of these hold: every check rule 9 requires, including `Greptile Review`, has succeeded on the current head without a substitute; Greptile and Codex review have both reviewed that head, or a head it moved from only by a merge of `main` without conflicts and with nothing else in the merge commit (ask `@codex review` after a later push); every P0 or P1 from either bot or the subagent is fixed in the head, or the subagent explains why it does not apply and the author posts that explanation on the pull request; and every `Review: REQUEST CHANGES`, including one from the author's subagent, has its findings fixed or its reviewer agrees they do not apply. The author posts every subagent verdict as given, naming it `by <login>'s code-review subagent (own pull request)`. For a collaborator named in Roles, the exception does not cover pull requests that change governance files or workflows (rule 12), or release pull requests. The owner or a maintainer may still review after the merge; a finding then becomes an issue. After the approval, any collaborator with write access, the maintainer or the owner may merge. Governance files and workflows also need the owner's approval of their content (rule 12), and releases follow [Releases](#releases). With write access, push your branch to this repository rather than a fork: both review bots run on pull requests whose head branch is in this repository, whoever opens them, and nobody needs an account of their own. Codex review does not run on pull requests from forks, while Greptile reviews both. When either does not review a pull request's head (a fork, a failed or stuck run), the reviewer runs a code review of that head itself, such as a local Codex run or its agent's code-review subagent, and posts the result on the pull request in its place.
9. **Before a merge.** Anyone who may review (rule 8) may take any pull request marked `Ready for review <sha>` that they did not write: comment `Reviewing: <GitHub login or agent>` first, so two reviewers do not do the same work, and say so if you stop. [CONTRIBUTOR-PATH.md, step 11](docs/CONTRIBUTOR-PATH.md#11-review-and-merge-someone-elses-pull-request) gives the commands. The reviewer:
   - reads the whole diff against the issues on the first lines of the body: those issues, nothing extra, and no bug fix in a feature pull request;
   - reads the Greptile and Codex review findings, or its own code review where a bot did not review the head (rule 8): every P0 or P1 is fixed in the head, or the reviewer says on the pull request why it does not apply;
   - comments on the pull request `Review: APPROVE <full head sha>` with what was verified, or `Review: REQUEST CHANGES <full head sha>` with the findings, naming itself (`by <GitHub login or agent>`). A later push needs a new verdict, unless it only merges `main`, without conflicts and with nothing else in the merge commit.

   Whoever merges:
   - merges only when the latest verdict approves the current head, or a head the branch has since moved from only by such a merge of `main`, once impact planning, CI validation, every selected CI job, every other applicable workflow in `.github/workflows/` and the `Greptile Review` check have succeeded for the current head, not only the checks GitHub marks as required. When Greptile did not review the current head (rule 8), the reviewer's own code review posted on the pull request for that head stands in for the `Greptile Review` check. Only groups explicitly omitted as unaffected by the plan may be skipped; skipped, neutral, cancelled or missing selected checks are not passes. The merge is a squash merge of the current head, never with `--admin`: `gh pr merge <N> --squash --match-head-commit <head sha>` (GitHub deletes eligible same-repository branches; a fork owner may need to delete their branch);
   - then comments on each closed issue with the merge commit and the evidence.

   A pull request that reports an unrun check as passed is not ready to merge. It lists unaffected omitted groups as not run, with the plan; any applicable check left unrun still blocks merging. A merge with no `Review: APPROVE` for the merged head, or for the head it moved from only by such a merge of `main`, breaks this rule: the reviewer opens an issue (rule 11) and reviews it after the fact.
10. **At most two open pull requests per author, and eight in all.** The author is the agent named on the `Author:` line, the words before its first comma, ignoring case and backticks. An agent that a coordinating session dispatches adds its lane in brackets, the name of the session that sent it (`Author: codex (phase1), fix/x`), and each agent and lane together counts as one author, so two sessions that both send work to Codex do not share its two slots. Drafts count. Release pull requests, governance pull requests (rule 12) and pull requests the owner labels `cap-exempt` do not count. Older pull requests keep their slots: the PR check fails the newest one over a limit. Check `gh pr list --state open` first, split large work into step pull requests (rule 2), and open the next step when one of yours has merged. If yours does not fit, close it and later open a new pull request from the same branch, or keep your claim `waiting for a slot`. Do not reopen the closed one: GitHub keeps its first creation time, so it would take a slot ahead of newer pull requests. A pull request from outside the team counts apart from the team's: at most two open per GitHub login and four in all, and the exemptions above do not apply to it.
11. **Undoing what a merged pull request did** needs an issue that names that pull request. A revert also goes through a pull request.
12. **Governance files** (`AGENTS.md`, `CONTRIBUTING.md`, `.github/`) change only with the owner's written approval of the content, file by file: in a comment the owner writes on the issue or the pull request, or in a chat with the maintainer. The pull request body quotes the owner's approving words, and nothing else from the chat, with their date and where they were given. It is then reviewed and merged as in rules 8 and 9, as for any other pull request. A workflow can widen what CI is allowed to do, so a pull request that changes `.github/workflows/` needs the owner's approval for each workflow file it changes before it is merged. A change to the text after the approval needs a new one. An agent's comment is not approval, and while agents post from the owner's GitHub account, a comment counts only when the owner confirms to the maintainer that it is theirs.
13. **The PR check.** `scripts/pr-check.mjs` runs on every pull request (`.github/workflows/pr-check.yml`), using the copy on `main`, and says in words what is missing and how to fix it. A pull request whose PR check fails is not ready for review. If you think the check is wrong about your pull request, say so in a comment; change the check only in its own pull request.
14. **Handing over.** If you stop before the work is done, push your branch and comment on each of your issues `Handover: <branch>, done: …, left: …, checks run: …`, then remove `claimed` from each. Your claims end there. The next agent claims the issues as in rule 3 and may continue on your branch.

### How the maintainer organizes the work

The owner names one Claude Code session maintainer of this repository. It plans and triages, and reviews and merges alongside the collaborators (rule 8); implementation goes to other agents.

- **Triage.** The maintainer, or a collaborator with write access, reads each new issue, sets its milestone and labels, and writes `Executor`, `Acceptance tests` and `Blocked by` into the issue body (the Task form has these fields). They add `ready` when an agent can start, and `blocked` while something must land first. A change of scope is an edit to the issue body with a dated `Updated:` line, not only a comment.
- **Review.** Every pull request gets a review of its diff by someone other than its author, or, for a pull request by the maintainer or a collaborator named in [Roles](#roles), by a code-review subagent its author runs under rule 8's conditions: a collaborator, the maintainer, such a subagent, or the owner. The verdict is posted as in rule 9.
- **Merge.** A collaborator with write access, the maintainer or the owner merges after an approval (rules 8 and 9); a governance pull request, workflow changes included, only once the owner has approved its content (rule 12).
- **Questions.** Ask on the issue, in a comment starting `Question:`, and add the `question` label. The maintainer answers in the same issue, in a comment starting `Answer:`, and removes the label. Only an answer on GitHub counts: a chat, a log or a notes file the asking agent cannot read is not an answer. While you wait, keep working on what the question does not touch, or hand over (rule 14).
- **The owner.** A question only the owner can decide gets the `needs-owner` label; the maintainer asks the owner and writes the answer in the issue.

## Images

README pictures are SVGs that `bun docs/preview/render.ts` draws from synthetic data with the board's own code, in the README's own language, with alt text that says synthetic; README pictures use their dark version, the same look as the social preview. Never hand-edit a generated SVG. Do not add a gallery to the guides. Historical assets remain in `docs/images/`. `node docs/preview/png.mjs` renders social previews; its fonts/tool requirements are documented in the preview sources. A synthetic render is not native acceptance evidence. Keep bearer URLs, conversations and private identifiers out of public images.

## Releases

The full checklist, what makes a release stable, and the npm steps are in [docs/RELEASING.md](docs/RELEASING.md). In short:

1. Update `.claude-plugin/plugin.json` and `package.json` to the same version, the three README badges and concise marketplace descriptions. Keep support claims aligned with evidence.
2. Run `node scripts/changelog-fold.mjs x.y.z` to see what it will do, then `node scripts/changelog-fold.mjs x.y.z --write`. It moves every fragment in `changelog.d/` and any entry left under `## Unreleased` into `## x.y.z — YYYY-MM-DD` and removes the folded fragments.
3. Fetch tags (`git fetch --tags origin`), then run `bun scripts/build-released.ts` with Bun 1.4.2. It records this version's generated-file ownership; do not edit its output manually.
   Run `bun scripts/build-board.ts`, then regenerate the released table once more. Both `--check` commands must pass together. The bundle omits its mutable pre-tag fingerprint and its own exact tagged fingerprint. Newer source with the same manifest version includes the frozen tag's fingerprint so upgrades still recognize it; historical board and command ownership remain included.
4. Run applicable checks and generated-file checks, including `node --test tests/npm-package.test.mjs`, which fails when `package.json` and `plugin.json` disagree. State any unavailable full SDK typecheck.
5. Open a regular PR titled `chore(release): Agent Board x.y.z` (pr-check treats a title starting `chore(release):` as a release). The reviewer verifies it as in [Pull requests](#pull-requests) and, under the owner's authorization, squash-merges the exact tested head (`--match-head-commit`) once every CI job is green.
6. On the merged release commit, run `claude plugin tag . --dry-run`, then `claude plugin tag .`. Push only the new exact tag, for example `git push origin agent-board--v0.23.0`. Never replace an existing release tag or push unrelated local tags.
7. Pick the channel by the release gate in docs/RELEASING.md. A stable release gets a GitHub release marked Latest and npm's `latest` tag; any other release is a GitHub pre-release and npm's `next` tag. Write the GitHub release notes from the version's CHANGELOG section, with a link comparing the new tag to the previous one. Only the owner publishes to npm, from the exact tagged commit, typing the one-time code; agents never run `npm login` or `npm publish`.

## Support matrix

Keep README, setup and messaging capabilities synchronized across languages. Distinguish native activity, explicit task reports, web/terminal UI and live receiving. Record actual version/platform/surface evidence and keep unsupported or untested adapters visible. Do not turn a generated configuration or another vendor's successful test into a blanket support claim.

## Bug reports

Prefer a synthetic reproduction, the Agent Board/affected host versions, CLI/App/IDE, OS and expected/actual behavior. Claude's version is relevant only to its optional plugin. Do not request raw real progress or conversation files. Report sensitive findings privately as [SECURITY.md](SECURITY.md) describes.
