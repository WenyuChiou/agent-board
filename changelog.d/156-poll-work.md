- **An idle poll is down to a few file checks, and one file read that never answers no longer stops the 2-second poll from redrawing (#156).** The pane still read the questions file and its companions every 2 seconds when nothing had changed. It now reads the questions again only when progress.md, a question file or the folder listing changed by name, size or time, when a file there was written within the last poll, or when the folder does not list. On a test board of 300 blocks, 100 live sessions and 1,000 question records, an idle poll made 17 file operations before this change and makes 5 now; the test holds it to at most 6, the check that #222's journeys left skipped. No file call has a time limit of its own, so one read that never returned (a drive that went away, say) kept the pane from polling again for good. A poll still running after 15 seconds now gives way to a new one at the next 2-second tick, and what its held read of progress.md brings back late is dropped; the questions are waited on for one poll at most, so the line under the prompt and the pane are drawn while a read is held up. While one poll that gave way is still held, no other gives way, so a file that stays held does not gather a read every 15 seconds; the polls run after a write return at once while one is held, as before, so writes do not wait on the held poll. One question pass runs at a time, from every caller; the poll and the timer skip it while one runs, and no pass starts beside a held one, so the inbox drain is not left behind passes piling up on a slow drive. While a read of the question files is held, no question is recorded (the drain keeps an agent's question saved meanwhile), and a press that needs the question list says it could not be read after 15 seconds. The pane's archive also keeps only the newest three torn questions files (the copies set aside when the file was cut off or garbled), and removes a temporary copy that an interrupted write left once it is a day old and the questions file itself reads; at most 200 of these go in one sweep, the rest at the next. A block with no end marker in progress.md, left by a write that never finished, held every question pass back for good, so the pane showed a red line that the question list could not be read and said an agent's question was still being saved, retrying. A block with no end marker that a `##` heading, a block start or a block end follows, or any block with no end marker once progress.md has stayed unchanged for 10 seconds, was cut off: such a block now ends where the reader ends it, the questions are read, its own questions stay as they were across every cut-off span (even when its own lines end in a cut marker) until it has its end marker again (none is counted as answered or gone, and none is recorded anew), and the pane, progress.html and the text board list it in plain words by agent and date under a folded Board health section or on a muted line at the bottom (left out of `--chat`, with the end-marker steps in the guide's troubleshooting section); while the file is still changing, a block followed only by other text or at the very end of the file may still be being written and is waited for. A writer used to delete a hand-kept task put right under a marker with no end, and now only the marker line goes: when the pane, a local reporter or `merge.py` updates or removes a block with no end marker, it replaces or removes only the opening marker line and leaves the lines below it and every section after them byte for byte, while another session's block is rewritten in its place, a new block goes below the cut-off block and a finished block after it is archived alone. A torn questions file over a week old now also goes at the sweep, even among the newest three, and a name moved aside by hand with a date (`.torn-2026-10-19`) goes by the file's own time. Moving a torn questions file aside and rebuilding it no longer raises the question-list error, and that error now waits until failed passes have lasted 10 minutes in a row and points in plain words to checking free disk space. A sweep that another agent's writes made try three times no longer leaves a block that asks in progress.md after an earlier try put its copy in the archive: the last try, which checks no question, still takes such a block when it reads as it did then, so the block is in one place and counted once; one changed since stays for the next sweep. This holds for `--tidy` and for the pane's own sweep. Even a block cut immediately after its opening marker keeps its question records and shows only their full saved questions; the error still needs three failures or fifteen races as well as ten minutes, and a clock moved back starts that wait again. Only a cut-off block's question records are held, not the board: its `[?]` steps stay in Waiting on you, each by its full saved question when one covers it (never by the cut-off words, and still hidden if the person hid it) and otherwise as written, not yet recorded; one whose questions are all answered or hidden, or one that is working, keeps its row with its steps. A saved question counts as covering a cut-off block's step only when it is that step's own question: one saved question fits it, and an answered one has the step's question token or came from the same inbox turn; a question asked again, or a different one cut to the same start, shows as written, since a question that should show but does not is worse than one shown twice. So a question the person hid shows again while its block is cut off when its step has no question token and its inbox turn is gone, until the block is whole. A question an agent's turn left waiting to be saved, for a block cut off before its question line, stays saved until the block is whole and the question is recorded (or, as any saved question, for 3 days), where it used to be dropped even when its inbox file was already gone; while it waits, an idle poll does not read progress.md again for it. Restoring those saved questions at session start is waited on for 15 seconds at most, like the first poll, and a sweep of torn ledgers that fails part way ends that archive sweep instead of starting another 200 removals.
