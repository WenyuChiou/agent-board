On Windows npm installs the check found no `codex.exe` on PATH, only the `codex.cmd` shims. And each request had only 1 s, while Codex's app-server can take longer to start. Now the check runs the Codex binary inside the npm package that `codex.cmd` points to. It never runs the shim itself, and a shim or link that leads outside the package is refused. An approval Codex has confirmed is remembered together with the sha of `hooks.json`, and when Codex cannot be asked, it holds while `hooks.json` is unchanged. A Codex that answers that the hooks are not approved, turned off or not listed still gets the instructions. So does one that cannot be asked after `hooks.json` changed. Upgrade note: a home whose last 0.23 connect confirmed the approval keeps it, even when the first check after the upgrade cannot run, as long as that connect leaves `hooks.json` as it was. The first connect whose check succeeds removes instructions that an earlier connect put back. Codex's warning about loading hooks from both `hooks.json` and `config.toml` comes from hook definitions in `config.toml`. Agent Board writes only approval records (`[hooks.state]`) there and never hook definitions, so that warning has another source, and this release does not change `config.toml`.
