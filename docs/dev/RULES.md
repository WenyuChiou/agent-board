# Agent Board rules, on one page

Every person and every agent reads this page first. The longer pages ([CONTRIBUTING.md](../../CONTRIBUTING.md), [team-process.md](team-process.md), [RELEASING.md](../RELEASING.md), [CONTRIBUTOR-PATH.md](../CONTRIBUTOR-PATH.md)) explain the details. When one of them changes a rule here, it changes this page in the same pull request; the PR check fails otherwise (R5). Each rule is written in one place: [docs/README.md](../README.md) lists every file and what it is for, and another page links to a rule instead of repeating it, so two copies cannot drift apart.

## Start here

- **What it is.** Agent Board shows what every coding agent on a computer is doing, on one board. Try it: `npx @wenyuchiou/agent-board setup`.
- **Find work.** Take an open issue labelled `ready` that has no assignee. The team assigns itself: that is its claim (R4). A contributor outside the team, who cannot assign themselves, claims with a `Claim:` comment ([CONTRIBUTING rule 3](../../CONTRIBUTING.md#pull-requests)). Work mainly on your own issues.
- **Talk on the issue.** Questions, hand-overs and decisions go in comments on the issue or its pull request. If it is not on GitHub, the next person cannot see it.
- **What a feature must be.** The owner's product rules are in [product-principles.md](product-principles.md). Read them before you design or change anything that a person or an agent sees.
- **Done means closed.** The pull request says `Fixes #N`; the issue closes when it merges, with how the change was checked.

## Every agent follows the same rules

- Claude Code, Codex, Antigravity, Cursor, cloud agents such as dot and Muse, and people by hand all follow this page. No rule here depends on which agent you are.
- **Where an agent starts.** [AGENTS.md](../../AGENTS.md) is the entry point; it sends you here first. Codex, Antigravity and Cursor read `AGENTS.md` by themselves. Claude Code does not: the repository is also a Claude Code plugin, whose root `CLAUDE.md` is not loaded, so a Claude Code session is given this page's link in its first prompt, or its user adds `@AGENTS.md` to their own `CLAUDE.md`. The same goes for any other agent that reads neither.
- **An agent works in the role of the person who runs it** (CONTRIBUTING, [Roles](../../CONTRIBUTING.md#roles)). An agent of the owner or of a collaborator may review and merge other authors' pull requests, as that person may.
- **One GitHub account, many agents.** The owner runs many different agents from one GitHub account, and a collaborator may do the same from theirs, so GitHub cannot tell the agents apart and its own approval button is not used. The `Author: <agent>, <branch>` line of a pull request says who wrote it, and the `by <name>` of a `Review:` line says who reviewed it. Name the agent and where it runs, as in `claude (desktop)` or `codex (superd6)`. A person working by hand writes their own name, as in `Author: eric, <branch>` or `by eric`; when a person has an agent do the work, the agent's name goes there.
- **Who counts as the author.** The agent named in the `Author:` line, every agent it dispatched, and every agent that wrote part of the pull request or its brief. Any other agent or session, of the same person or not, is not an author and may review it; whether its approval counts depends on the pull request's tier (R2). One agent the lane dispatches is not an author: a read-only reviewer it starts new only to review the pull request, which writes and briefs no part of it. That reviewer is still in the author's lane, and its approval counts only where R2 says: on a light-tier or normal-tier pull request. A reviewer the maintainer starts new for a risk-tier pull request is not an author either, and its approval counts on the maintainer route. Nor is the Fable subagent that writes a pull request's case table (R6): the table lists events, states and expected results, and no design or code (owner, 2026-11-15; #1503).
- **One driver per pull request.** The agent in the `Author:` line drives its pull request to the merge. Another agent continues it only after a `Handover:` from that agent ([CONTRIBUTING rule 14](../../CONTRIBUTING.md#pull-requests)), or after 24 hours with no word from it, or when a team author has neither pushed nor replied within 6 hours of a `Review: REQUEST CHANGES` ([team-process, From claim to merge](team-process.md#from-claim-to-merge)); it then adds its own name to the `Author:` line and says so in a comment. Two agents never push to one branch at the same time.
- **Status goes in the body.** After a push, update the pull request body's Evidence for the new head instead of posting a status comment. Comments on a pull request are for `Ready for review`, `Reviewing:`, `Review:`, `Handover:`, `Question:`, `Round cap:` and `Consistency check:` lines, and for answers to review findings.
- **Nobody waits idle.** While a pull request waits for a review or CI, its author takes independent work first: the next `ready` issue on a new branch from `main`, or a review it may take. The waiting pull request still gets its review fixes, conflict merges and handover ([team-process, From claim to merge](team-process.md#from-claim-to-merge); owner, 2026-11-11).

## R1. Who decides what

- The owner (Wenyu) sets direction: the roadmap, the must-ship issues of each milestone, and rules R2 and R3. A question that only the owner can answer gets the `needs-owner` label; there should be few.
- The owner's approval is needed only for what decides who may approve and merge, and what CI may do: `.github/workflows/`, sections R2 and R3 of this page, CONTRIBUTING rules 8, 9 and 12, and the team-process sections From claim to merge and Standing approvals ([CONTRIBUTING rule 12](../../CONTRIBUTING.md#pull-requests)). The roadmap is the owner's too (above): issue #209 and [universal-messaging-roadmap.md](universal-messaging-roadmap.md). So are the product rules in [product-principles.md](product-principles.md).
- **The owner writes the owner's approval by hand.** No agent posts an approval in the owner's name, not even when the owner asks for it in a chat: the owner writes it on the issue or the pull request themselves (CONTRIBUTING rule 12; owner, 2026-11-03).
- **The maintainer** reviews, merges and releases, and plans no other lane's work. It is the Claude Code session the owner names (CONTRIBUTING, [Roles](../../CONTRIBUTING.md#roles)). No agent decides scope or order for another. The issue's milestone and labels set the order; when two agents disagree, the reviewer decides, and only a question about the roadmap or a milestone's scope gets `needs-owner`. A comment on someone else's pull request from anyone not reviewing it is advice.
- Everything else is decided by the people doing the work: collaborators, the maintainer session and their agents. A change to process details (labels, merge order, wording) needs one approval from an agent or person who did not write it.

## R2. Nobody approves their own work

- The author never approves their own pull request. A review bot (Codex Code Review, Greptile) never approves one on its own. A bot's unresolved P0 or P1 stops a merge until someone other than the author resolves it, or the author answers it on the pull request with evidence that the reviewer accepts (owner, 2026-11-12; #1375).
- **Lanes.** A lane is the owner or a collaborator (anyone the owner has given write access to this repository, CONTRIBUTING rule 8) working by hand, or one of their agents, together with every agent it dispatches or briefs, such as the maintainer session and the agents it starts, dot, Muse, or a Codex or Antigravity run. A contributor without write access has no lane: a reviewer from the team reads their pull requests. **Outside a lane** means a person, or a session started new for the review, that wrote no part of the pull request or its brief, and that the lane did not start.
- **The approval** is the comment `Review: APPROVE <full head sha> by <reviewer>, lane <reviewer's lane>`. The pull request's tier says who may write it. The highest tier that any of its changes reaches applies, except that a release pull request, and every pull request of a lane under risk-tier review after a P0 or P1 (below), is risk tier whatever it changes. The body names the tier on a line `Tier: risk`, `Tier: normal` or `Tier: light`, and its authors' model family on a line `Authors: <family>`: one or two of Claude, GPT, Meta, Gemini, or a person. The reviewer checks both, and the reviewer the maintainer starts for a risk-tier pull request follows from the `Authors:` line (owner, 2026-11-10; owner, 2026-11-12; #1375).
  - **Risk tier.** The change touches what a person's configuration, permissions, tokens, data deletion, setup or hooks depend on, or any path in [risk-paths.md](risk-paths.md), which is part of this rule; a change to one of the large shared files that list names is risk tier only for the four things it lists. After the lane's `Ready for review <full head sha>`, a reviewer the author's lane starts new for this review may approve it, of any model family, as "A lane's own reviewer" below says: the Codex review bot's review of the same head is the check by another model family (owner, 2026-11-28; #1974). A reviewer of another model family than every author, such as Codex reading a change Claude wrote, is welcome, not required. The maintainer may also take it at once (the maintainer route, below). A release pull request takes neither: a reviewer outside the maintainer's lane, or the owner, approves it. A lane under risk-tier review after a P0 or P1 (below) takes the maintainer route. A lane has only agents of the author's model family write any part of a risk-tier pull request or its brief (owner, 2026-11-12; #1373): a Claude lane has Claude subagents write its fixes, a Codex lane has Codex runs write them, and an agent of another family only reviews it, unless it takes the pull request over as "One driver per pull request" (above) and [team-process](team-process.md#from-claim-to-merge) allow, such as after the third round. When its authors (as counted above) are of two families, as after such a takeover, a reviewer the maintainer starts is of a third family (Muse, or a Gemini run, for one Claude and Codex wrote); a lane's own reviewer, under the conditions below, or the owner by hand, may approve it too. The pull request adds a test that fails without the change; a change with no behaviour a test can show, such as governance text or a CODEOWNERS line, says so in its body instead. With a case table, required by R6 or not, from #1521 on, the body's `Fail-first:` line, printed by preflight for the head, shows it for the new or changed Node tests the table names by a fixed title: each fails on the merge base and passes on the head. Named tests it cannot run there are listed, not counted, and when it runs none the body says `Fail-first: none, <reason>` ([CONTRIBUTING rule 8](../../CONTRIBUTING.md#pull-requests), #1520).
  - **Normal tier.** Everything that is neither risk nor light. The reviewer is outside the author's lane: someone in another lane, or a reviewer another lane starts. Or a reviewer the author's lane starts new for this review, of any model family, as below (owner, 2026-11-12; #1375).
  - **Light tier.** Only docs, tests, copy and the string tables. A read-only reviewer that the author's lane starts new for this review, of any model family, may approve, as below.
- **A lane's own reviewer**, wherever R2 lets one approve: on the light, normal and risk tiers (never on a release pull request, nor on a pull request of a lane under risk-tier review after a P0 or P1), and, started by the maintainer, on the maintainer route. It is a read-only Codex run or a subagent, started new for this review: never a resumed session or agent that wrote or briefed any part of the pull request. Its verdict line says it was `started new for this review` (`Review: APPROVE <full head sha> by codex (read-only, started new for this review), lane <lane>`), which is how the PR check tells it from the author approving. It writes nothing, so the lane (on the maintainer route, the maintainer) posts its comments for it: its `Reviewing:`, its verdict and, when it is the Codex run below, that run's result. Its verdict counts only when:
  - the reviewer read the exact head the verdict names, and read for itself on GitHub the issues named on the pull request's first lines and the test evidence for that head (its CI runs and the preflight output in the body), not a summary the lane wrote. Every review, apart from a first review that stops at a gap in the case table (below), reads the pull request's whole diff against the issues on its first lines ([CONTRIBUTING.md](../../CONTRIBUTING.md#pull-requests), rule 9) and, on the risk tier, reads in full every changed file whose change makes the pull request risk tier: each file [risk-paths.md](risk-paths.md) lists, and any other file whose change reaches what the risk tier covers, a large shared file that list leaves out included. The first review of a pull request reads the head in full; on a pull request with a case table it reads the table and its tests first and stops there when they have a gap ([team-process, The case table](team-process.md#from-claim-to-merge)). Such a review read no head in full, so the next review reads the head in full. A later review reads every earlier verdict with its findings and the answers, and, in full, every file that the diff since its own last verdict's head touches (for a reviewer new to the pull request, the last head any verdict names), conflict resolutions of `main` merges included. It reads the head in full again when the diff since the last head a reviewer read in full has more than 300 added and removed lines together, outside tests and generated files (owner, 2026-11-13; #1421; #1927);
  - the reviewer read every P0 or P1 finding on the pull request, from a bot or anyone else, and every `Question:` about it, on the pull request or on an issue named on its first lines, each with the author's answer, and agrees that each finding is fixed in the head or does not apply, and that each question is answered. A finding or question settled this way does not wait for whoever raised it to come back; a question only the owner can answer (R1) still waits for the owner;
  - on the risk tier, the head the verdict names meets the conditions the maintainer route lists below (the `Greptile Review` check, the Codex review bot's review of that head, every bot P0 or P1 settled, the test that fails without the change). When the Codex review bot did not review that head, the lane asks it with a `@codex review` comment; when it still has not after an hour, a read-only Codex run started new for that head reviews it and the lane posts the result, or the lane hands the pull request to the maintainer route (owner, 2026-11-28; #1974);
  - the reviewer approved. When the lane disagrees with one of its findings, the approval comes from a reviewer outside the lane. The lane posts every verdict its reviewers give, `Review: REQUEST CHANGES` included, followed by every finding the reviewer reported, or "no findings", and what was done with each (applied in which commit, or not applied and why), then each P0, P1 and `Question:` from others with a link to its answer; a reviewer it starts later for the same pull request is given every earlier finding as posted: a lane does not keep starting new reviewers in search of an approval.

  A P0, P1 or `Question:` that arrives after the approval holds the merge until a reviewer the lane starts new for it, given every earlier finding, agrees as above that it is fixed or answered.
- **The maintainer route, on the risk tier** (owner, 2026-11-12; #1375). After the lane's `Ready for review <full head sha>` for the current head, the maintainer may take the pull request at once instead of the lane's own reviewer, and takes it when the lane hands it over; nobody waits two hours. Since 2026-11-28 the route is an option for every lane but one under risk-tier review after a P0 or P1, which still takes it (owner, 2026-11-28; #1974).
  - The maintainer reviews it itself when it is of another model family than every author of the pull request (authors as counted above, brief writers included).
  - Otherwise the maintainer starts a reviewer of another model family than every author, under "A lane's own reviewer" above, and posts its `Reviewing:`, its verdict and its findings. For a pull request whose authors are of two families, that reviewer is of a third family: Muse, or a Gemini run.
  - For the exact head the verdict names, on this route and for a lane's own reviewer on the risk tier, the `Greptile Review` check succeeded on that head; the Codex review bot reviewed that head, or, when it did not, a read-only Codex run started new for that head reviewed it and the result is posted on the pull request; and every P0 or P1 thread from a bot is resolved by someone other than the author, or answered on the pull request with evidence that the reviewer accepts. The pull request also has the test that fails without the change, or its body says why no test can show it.
  - Anyone else outside the lane and outside the authors' families may still review it, and the maintainer does not wait for them. An outside reviewer's `Review: REQUEST CHANGES` still holds until that reviewer answers or it lapses ([team-process](team-process.md#from-claim-to-merge)).
  - The owner may approve by hand at any time. When the maintainer is away, a collaborator with write access takes the maintainer's place. A release pull request is approved by a reviewer outside the maintainer's lane, or by the owner; it never takes the maintainer route.

  The verdict of a reviewer the maintainer started ends with `, maintainer route`: `Review: APPROVE <full head sha> by <reviewer>, lane <lane>, maintainer route`. The maintainer's own review, a lane's own reviewer, and a reviewer outside the lane write no suffix. Every merge made on a `, maintainer route` verdict, and every risk-tier merge made on a lane's own reviewer's verdict, is read in full by someone outside the lane within one day of the merge, and RELEASING step 5 lists each one with its read before the release (owner, 2026-11-24; #209). Each new head, a merge of `main` included, needs a new verdict from the lane's own reviewer or the maintainer-started reviewer for which these conditions hold again.
- **A P1 found after the merge.** A P0 or P1 found in a merged pull request becomes an issue. From then on, every pull request of the author's lane takes risk-tier review, whatever it changes, and goes to the maintainer (the maintainer route, above; a release pull request still goes to a reviewer outside the maintainer's lane or the owner), until the owner lifts it by hand on that issue (owner, 2026-11-10, 2026-11-11 and 2026-11-12; #1375).
- Every tier keeps rule 9's conditions before a merge and rule 12's owner approval of governance files and workflows. A release pull request is risk tier ([RELEASING.md](../RELEASING.md)). Anyone may still review after the merge; a finding then becomes an issue.
- **A review stays on the pull request's issue.** Each finding in a `Review: REQUEST CHANGES` names the rule it breaks or the steps that show the bug. A finding with neither is advice: welcome, but it does not hold the merge.
- A later round checks the earlier findings and what the new push changed. After the pull request's first full read (the first review that read a head in full, not one that stopped at a gap in the case table), a new finding in code that an earlier round read, in lines no push has changed since, is a P0 or P1 only when its result is a message lost, sent twice or started in a turn already running, data lost, or a security problem. Anything else found there becomes an issue of its own, linked to the pull request, and does not hold the merge. A review bot's P0 or P1 there is read the same way: its thread is answered with that issue's link, and for the reviewer's conditions above and CONTRIBUTING rule 9 it counts as such an issue, not as a P0 or P1. The lines a push changed are those in `git diff <last head>..HEAD`, and every line of a conflict that a merge of `main` resolved, whichever side it kept. Code no round has read, such as an unchanged helper the change now calls, keeps the first-read bar (11-26 workflow review; #1918). So does a failure the new push causes, in any line: an unchanged caller that breaks because the push changed what it calls is the push's finding, not an old one (#1927). A later round resumes the same reviewer on the diff since its last head, not a new reviewer reading everything again, unless that reviewer's request lapsed or it is gone ([team-process](team-process.md#from-claim-to-merge)): then another reviewer takes the round with every earlier finding and the diff since the last head a verdict names (after a first round that stopped at a gap in the case table, the next round reads the head in full, as R2 says above): the maintainer sends that reviewer its earlier findings and `git diff <last head>..HEAD`, the last head being the one its last verdict names (#1544; #1927). A reviewer resumed this way still counts as started new for this review, because it wrote and briefed no part of the pull request and only the pull request's own earlier round started it; a reviewer that wrote or briefed any part is never resumed as one.
- A review bot's P0 or P1 that arrives after Ready is fixed, or the author shows on the pull request, with evidence, why it does not apply, or, in code and lines the later-round line above covers, it is answered with its issue's link as that line says; the reviewer decides.

## R3. Merging

- A pull request merges once every required check is green on its current head and a reviewer that its tier allows has approved that head, or, for a verdict CONTRIBUTING rule 9 lets carry over, the head it moved from only by a merge of `main` with no conflicts and nothing else (R2, CONTRIBUTING rules 8 and 9): someone outside the author's lane, or, on the light, normal and risk tiers (never a release pull request), its lane's own reviewer, or, on the risk tier, the maintainer route. Then anyone with write access may merge it, the author included: any collaborator, the maintainer, the owner, or any of their agents. Nobody waits for a particular person.
- A change to `.github/workflows/` also needs the owner's approval, because a workflow can widen what CI may do (CONTRIBUTING rule 12).

## R4. One issue, one owner

- The team assigns itself before it starts; one assignee per issue. A contributor outside the team claims with a `Claim:` comment instead (CONTRIBUTING rule 3). If someone is assigned or holds a live claim, comment on the issue instead of starting a competing pull request.
- An issue with no activity from its assignee for 24 hours may be unassigned by anyone, with a comment, and goes back to `ready`.
- **A plan is an issue.** Whoever has a plan opens an issue with its goal, what counts as done and the files it touches; a large plan becomes one issue per step.
- **Who adds `ready`.** Any agent or person on the team who did not write the issue may add `ready` to it, after posting a comment on it that starts `Ready check:` and answers five points: the goal is clear; the issue says what counts as done; no question is open and nothing it waits on is still unmerged; it fits the current roadmap (#209) and its milestone, with no conflict or drift; and its change fits one pull request within R6's size limit, or the issue says how it splits, or why it cannot (R6's `cannot split`). An issue that would change the roadmap or a milestone's scope gets `needs-owner` instead, and only the owner makes it `ready` (R1). A `Ready check:` that answers NOT READY names each point it misses; the next check reads those points and the issue's edits since. After two NOT READY checks in a row, the second checker posts a `Question:` to the issue's writer, or to the owner for a scope question, and no further check runs until it is answered; the same holds after each later NOT READY (#1927).
- One pull request is one feature, or up to three bug fixes, branched from current `main`. A finding outside your issue becomes an issue of its own: one from a pull request links that pull request, and one from an audit or a test run names the run. An issue that is opened, edited or reopened is flagged when its title matches an open issue with a lower number (`scripts/pr-check.mjs` and `.github/workflows/issue-check.yml`), and a pull request is flagged when its check runs if it fixes an issue that an open pull request with a lower number already fixes (`scripts/pr-check.mjs`, #1325). The check flags only the issue or pull request it runs on, so an older one changed to match a newer one flags neither.

## R5. Checks are code

- A rule that can be checked lives in `scripts/pr-check.mjs` or `scripts/review-queue.mjs`, not only in prose.
- A pull request that changes CONTRIBUTING.md, docs/dev/team-process.md or docs/RELEASING.md also changes this page, or says why not in a body line `Rules page: unchanged, <reason>`.

## R6. When something fails

- Before it fails: a risk-tier pull request changes one failure surface and names it on its `Surface:` line, with the exceptions [CONTRIBUTING rule 2](../../CONTRIBUTING.md#pull-requests) lists (two surfaces with a `cannot split:` reason the maintainer or the owner accepted, `none` for a lane's pull request that changes no surface, no line on a release), so review rounds do not chase new cases across surfaces.
- Size (owner, 2026-11-15; #1545): a pull request's changed lines, counted without tests, generated files and the string tables, stay at 400 or fewer on the risk tier and 800 or fewer on the normal tier, with a note above 400. pr-check fails one above its limit unless the body says why it cannot be split: `cannot split: <reason>` at the end of the `Surface:` line, or a line `Size: cannot split: <reason>`. The light tier and releases have no limit; it applies to pull requests numbered above 1545.
- Before the first push: a risk-tier pull request on the `delivery`, `setup-writes`, `data` or `launch` surface whose change handles an event that can arrive while another is still under way, or in more than one order (a connection lost or made again, a timer, an approval, a second writer, a late reply), has a case table from a Fable subagent before any code is written: one row for each such event in each state the change can be in, with the expected result and its test. The body carries it under `## Cases` with a line `Cases: <n> rows`, or says `Cases: none, <reason>`. Each row names its test by its exact title in backticks (a planned title on a draft), so pr-check can find it and preflight can run it when it is a Node test with a fixed title (from #1521). A review checks the head against the table, and a case a review finds becomes a row ([CONTRIBUTING rule 2](../../CONTRIBUTING.md#pull-requests), [team-process.md](team-process.md#from-claim-to-merge)).
- When the cause is still unknown after two fix attempts, stop and write a `Question:` on the issue.
- When two review rounds in a row find new cases of the same kind, the author stops patching after the second, and the maintainer gets a Fable diagnosis of the design ([team-process.md](team-process.md#from-claim-to-merge)).
- When a risk-tier pull request has had five review rounds (a round is one head with a `Review: REQUEST CHANGES`, counted over the whole pull request: an approval does not restart the count), it stops: the author pushes no further fix, the maintainer says in a `Round cap:` comment what is settled, that part merges after one more review, and each open finding becomes an issue named on the body's `Round cap: #A, #B` line. When the fifth round's findings are only in docs or comments, it gets one more round instead, and the body says `Round cap: one more round, words only` ([team-process.md](team-process.md#from-claim-to-merge)).
- **Rules pull requests** (owner, 2026-11-15; #1539). A pull request on the `rules-text` surface that changes no code, test or workflow is approved by the owner by hand: the owner's own comment `Review: APPROVE <full head sha> by owner`, naming each governance file it approves, is both its review and rule 12's approval of its content, and no agent reviews it. Before the owner reads it, the author may post one read-only consistency check by an agent that wrote no part of it, as a comment that starts `Consistency check:` and has no line that starts `Review:`, fenced or not, since pr-check reads any such line as a verdict: it names lines that conflict with another rules file or with what a check enforces, and it is advice for the owner, never an approval and never a review round (#1927). One that also changes code, a test or a workflow takes one review round as its tier says. After that round, a finding holds the merge only when it lets a check pass what the rules say it must fail, breaks CI on `main`, or blocks every pull request, or every pull request of one kind; any other finding becomes an issue the body names, and the reviewer judges the head without it. The round cap above still applies.
- A raised timeout, a skipped test or an added retry is never the fix for a flaky test.

## R7. Releases go out by themselves

Nobody gives a go-ahead for a release ([RELEASING.md](../RELEASING.md)). Every release, pre-releases included, needs:

- the release pull request merged as R3 says, with the version agreed in `plugin.json`, `package.json`, the README badges and the marketplace text, the CHANGELOG folded and the generated files rebuilt;
- **no hook changed in a patch release.** A patch release, one that changes only the last number of the version, never adds, removes or rewords a hook: neither one that setup writes into an agent's configuration nor one the Claude Code plugin registers (owner, 2026-11-11). A hook change waits for a release that changes the first or the middle number;
- **a simulated user.** An AI acting as a new user installs the release's package, sets up, opens the board and walks every journey, on Windows and on macOS or Linux, as [USER-SIM.md](../validation/USER-SIM.md) says. Its record is `docs/validation/<date>-usersim-<version>.md`. Any agent or person may run it. A FAIL, or a FRICTION step with no issue, stops the release. After a change to the release pull request's head, a run may cover only the journeys the change reaches; after two such runs in a row the next is full, and so is the run before a stable release. Once the run meant to be the last starts, nothing but the release pull request merges into `main` until the tag.

It goes out as **stable** when the release gate also passes on the tagged commit, and as a **pre-release** otherwise:

1. CI is green on Ubuntu and Windows.
2. The live parity record for the vendor apps exists ([PARITY-CHECKLIST.md](../validation/PARITY-CHECKLIST.md)); any collaborator with the apps installed may run it.
3. The L1–L3 journey tests pass (`tests/e2e/`).
4. Every must-ship issue of the milestone is closed.

The maintainer, or a collaborator when the maintainer is away, tags it and makes the GitHub release without asking. Publishing to npm needs the owner's one-time code until npm trusted publishing is set up; that is the one step left by hand. After a release, the owner answers the three next-version questions that `changelog-fold` prints.

## R8. What stays off GitHub

This repository is public: anyone can read every issue, pull request, comment, commit and CI log, and a deleted comment may already be copied.

- **Public here:** these rules and the process, the code, issues about the product, and validation records made with synthetic data.
- **Never anywhere in the repository:** tokens, keys, passwords and links that carry one. They live only in GitHub Actions secrets and environments. A leaked one is revoked first, then removed.
- **Kept off GitHub:** session logs and transcripts, write-ups of what went wrong in someone's session, anyone's home-folder paths, computer user names, email addresses and machine names, a person's own agent or harness settings, internal budgets such as GPU hours or spend, and anything someone said in private. They stay with the person they belong to, or in a private place the owner sets up and gives access to; an issue here says in plain words what the next person needs, without them.
- **Security problems** go to GitHub's private vulnerability report ([SECURITY.md](../../SECURITY.md#reporting-a-problem)), never to a public issue. Only the owner, and the people the owner adds to that report, can read it.
- **Checks.** The PR check fails a pull request that adds a home-folder path, a session id, a token or an email address to a document or its body. Once the owner turns them on in the repository's settings, GitHub's secret scanning and push protection will also stop a known kind of token before it lands; they are not on yet.
