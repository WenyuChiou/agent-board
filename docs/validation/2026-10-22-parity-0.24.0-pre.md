## Upgrade replay, on a copy of the board

What 0.24.0 will do to the owner's board on its first start, measured on a copy. The copy stays on the maintainer's machine, out of this record; only numbers are given here.

- **The copy:**
  - The real board as it was before the candidate first started: 461,913 bytes, 216 agent blocks and 70 waiting steps.
  - The 1,393 held inbox files: 1,367 Codex prompt, turn and end files from the 38 hours before, plus 26 set-aside and `.tmp` files up to 63 hours old. This run's 18 synthetic files were left out.
- **The run:** the candidate (main 14c0893) as the Claude plugin, in one `claude -p` session in the real home, with `CLAUDE_PROGRESS_FILE` pointing at the copy. The session stayed open for about 8 minutes.
- **The first sweep, at start:** it moved 29 blocks to the copy's archive for the month. The board went from 461,913 to 442,271 bytes.
  - **What moved:** 27 done blocks 20 to 51 hours old, one ended Claude block (111 hours) and one waiting Codex block (110 hours).
  - **The rules:** done blocks go after half a day, stopped ones after three days. This sweep followed them; nothing was archived or hidden against them, and every archived title is in the archive file.
- **The drain:**
  - **Speed:** it started a minute after the session did, and used up 224 files in 7 minutes, about 32 a minute. 68 more were claimed but not finished when the session ended.
  - **Projection:** at that rate, all 1,393 files need about 45 minutes of an open Claude session.
- **Rows:**
  - 35 Codex blocks added: 20 ended, 11 done and 4 waiting.
  - 9 existing blocks updated.
  - Waiting steps went from 70 to 79.
  - After the 7 minutes, the board was 460,253 bytes.
- **Time stamps:** every added block carries the time of the replay, not of its turn, although the drain takes the oldest files first and these were 35 to 38 hours old (see "New problems").

## New problems found

No issue was opened in this run. The PM files these.

1. **The candidate tells Codex to report through a fallback, although Codex's hooks already run.**
   - **Steps:**
     1. Start from a home where the 0.23.5 connect hooked Codex. Codex writes prompt, turn and end files to the inbox on every turn, and the connect record still says Codex trust is unconfirmed.
     2. Run the candidate's `/progress connect`.
   - **What the connect does:** it prints "Codex: reporting hook configured; approve it once in Codex's /hooks" and "Current Codex hook approval is unconfirmed. Check /hooks; existing managed reporting instructions are retained." It also adds a section to `~/.codex/AGENTS.md`: "Until these hooks are approved in Codex /hooks, report each meaningful work step as JSON on stdin to: node … --codex-report …".
   - **What happened next:** the owner's own Codex sessions reported both ways. Their hooks kept writing inbox files, and the fallback wrote 5 session records to `~/.agent-board/sessions` over 25 minutes, within the 45 minutes its section was in place, each marked as applied to the board.
   - **Expected:** one path per session. Either no fallback while the hooks fire, or a way for the connect to see that they fire.
2. **Codex warns about its hooks on every run.** `codex exec` reports "loading hooks from both …hooks.json and …config.toml; prefer a single representation for this layer".
   - Agent Board writes only `hooks.json`. This run did not read `config.toml`, so it does not say whether that file's hooks come from another tool.
   - **Steps:** run any `codex exec` turn on this machine.
3. **"Archive now" archives a hidden task without saying so** (related to #231).
   - **Steps:** on a board whose page lists 2 finished tasks, and which also holds a 3-day-old, fully ticked Hermes block in the waiting state that the page does not list, press Archive now.
   - **Result:** the page says "Archived 3 tasks." The hidden block went to the archive too, although the page never showed it.
4. **OpenCode connected by `setup-agent.mjs` reports under the wrong project.**
   - **Steps:** run `setup-agent.mjs --agent opencode --apply`, then `opencode run` in a folder named `project`.
   - **Result:** the board got a project "opencode" with the task "Local opencode task" and the step "Waiting for the next instruction", not the folder's name.
5. **`.tmp` files stay in the inbox forever.** The real inbox held 8 `.tmp` files from the 0.23.5 reporter, the oldest from 2026-10-19. The candidate's drain skips them, and nothing removes them. The third storage pull request for #156 lists `.tmp` clean-up.
6. **Held turns applied on upgrade carry the time they were applied.**
   - **Steps:** keep a board with an inbox of Codex turn files about a day and a half old, which 0.23.5 never applied. Start the candidate plugin on it, and let the drain run.
   - **Result:** each block it adds or updates gets `updated=` set to the moment of the drain. Questions from a day and a half ago come back as fresh waiting cards: waiting steps on the copy went from 70 to 79 in 7 minutes, net of the one waiting block the first sweep archived. Sessions that ended that long ago stay on the board three more days.
   - **Expected:** the turn's own time, so old turns land as old and the archive rules apply to them.
   - The measurement is to be repeated on the release candidate once #380's inbox cap merges.
