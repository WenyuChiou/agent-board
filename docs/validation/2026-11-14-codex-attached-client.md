# Codex: how can Send to Codex tell that a person's client is attached to a thread? (#318, 0.25.0), 2026-11-14

Research by a Claude Code subagent for the maintainer's PM session. CLI 0.167.0 and daemon 0.169.0 on Windows, read against `openai/codex` tag `rust-v0.169.0` and `origin/main` of agent-board at `c41f39f9`. No model turn was used. No ids, tokens or home-folder paths below.

## Answer

The daemon has no call, count or notice that says "a client is attached to this thread". The only trace is indirect: the daemon keeps a thread loaded while at least one connection is subscribed to it, and unloads it (`thread/closed`) 60 s after the last subscriber left and the thread is idle (default `thread_unload_delay_secs = 60`). So the recommended check is: **the receiver stays unjoined while it waits, and treats a thread as "a person is attached" only when `thread/loaded/list` still lists it without the receiver's own subscription.** It joins (`thread/resume`) only to deliver a turn and leaves (`thread/unsubscribe`) when the turn ends. Today's receiver joins right away and stays joined, which keeps the thread loaded for ever after the person quits (live-confirmed below); that is why the closed-window run got a turn. Confidence: high for the daemon side (source read plus live runs with a real Codex TUI and with raw protocol clients, all with zero model turns); medium for the whole design, because (a) a person who quit less than 60 s ago still counts as attached, (b) any other subscriber (a second board page, another tool) also counts, and (c) the receiver's join-then-leave sequence around a delivery has not been run with a model turn. Pair it with an approval watchdog (Option 3) for the 60 s window.

## Evidence

### 1. What the protocol exposes (CLI 0.167.0 schema, daemon 0.169.0)
- Generated with `codex app-server generate-json-schema` (writes into a scratch folder). Thread methods: `thread/loaded/list` (params `cursor`, `limit`; answer is only `data: [thread id]`, "Thread ids for sessions currently loaded in memory"), `thread/read`, `thread/resume`, `thread/unsubscribe`, `thread/status/changed`, `thread/closed`, `thread/started`, `thread/readState/changed`, `thread/queue/changed`, `thread/settings/updated`. No list of connections or clients, no subscriber count, no attach or leave notice. `thread/attachment/*` is persisted file attachments, `thread/environment/connected` is an execution environment: neither is a client.
- `ThreadStatus` values: `notLoaded`, `idle`, `systemError`, `active` with `activeFlags` from `waitingOnApproval` and `waitingOnUserInput`. Sent as `thread/status/changed` (only to subscribers, except the closing pair, below) and returned by `thread/read` and `thread/resume` as `thread.status`.
- `thread/unsubscribe` answers `unsubscribed`, `notSubscribed` or `notLoaded`: it tells the caller about its own subscription only.
- `thread/started` and `thread/closed` (with `thread/status/changed` to `notLoaded`) are sent to **every** connection, subscribed or not (live: a connection that never joined got both).
- `README.md` of `codex-rs/app-server` says "thread/unsubscribe or disconnect stops delivery" (about read-state notices); it names no attached-clients feature. `turn/start` and `thread/resume` take `approvalPolicy` and `approvalsReviewer` overrides ("for this turn and subsequent turns").
- Source: `codex-rs/app-server/src/request_processors/thread_lifecycle.rs` (`UnloadingState`, `unload_thread_without_subscribers`), `thread_processor.rs` (`thread_unsubscribe_response_inner`, `connection_closed`), `codex-rs/config/src/config_toml.rs` and `codex-rs/core/src/config/mod.rs` (default 60). `has_subscribers` is used internally only; no request returns it.

### 2. `thread/closed`
- Sent when a thread was unloaded: no connection subscribed AND not active, for `thread_unload_delay` (60 s by default) counted from the later of "last subscriber left" and "last became inactive" (`unloading_target`). The thread is shut down, removed from `thread/loaded/list`, `thread/status/changed` (`notLoaded`) then `thread/closed` go to all connections. Also sent for threads unloaded by a workspace switch (README, "accountSession/switch").
- Rejoin afterwards: `thread/resume` by id loads it again from its saved history. Not possible for a thread that has no saved history yet (live: `no rollout found for thread id`; the receiver's own comment says the same).
- Live (a separate test home, own daemon, two raw protocol connections, no model turn):
  - Last subscriber's connection dropped: still listed for 60.7 s, then `thread/status/changed notLoaded` + `thread/closed` to the connection that never joined (and `thread/loaded/list` empty).
  - Explicit `thread/unsubscribe` (answer `unsubscribed`, a second one `notSubscribed`): closed 61.1 s later.
  - A subscribed, idle thread stayed loaded for the whole 75 s watched, no notice.
- Live with the real TUI (`codex resume <old session>` in a pseudo-terminal this run started; no prompt, so no turn, the saved session file was unchanged): the thread was listed to an unjoined connection for the 60 s it watched while the TUI sat open and idle; after the TUI quit ("Disconnected from this task"), still listed for the next 60 s, then `notLoaded` + `thread/closed` 61 s after the quit.
- Live, the receiver's situation: a connection joined (`thread/resume` with `excludeTurns`, which answered with a `thread/goal/cleared` notice, the first notice the earlier closed-window log shows), the TUI quit, and the thread stayed loaded for the 110 s watched. So a joined receiver keeps the thread alive for ever and hides that nobody is attached.
- The earlier unexplained `thread/closed` + `thread/status/changed` while the client was open: by the source, a thread closes only after 60 s with no subscriber, and that does not fit a joined thread. The earlier log keeps only the method name and a "has a thread id" flag, not the id, and `thread/closed` goes to all connections, so the pair was most likely for another thread on the daemon (the first turn's thread had finished at about the time the 60 s began). **Not proven**, see Not known.

### 3. How the receiver decides today (`scripts/codex-receiver.mjs`, `origin/main`)
- Tick (3 s): `threads()` from the board, `loadedThreads()` (`thread/loaded/list`), and for each wanted loaded thread `attach()` (line 199): `thread/resume {excludeTurns:true}` joins it, the status starts from the answer, `thread/status/changed` and `turn/*` notices keep `state.status` and `state.turn`. Ready = `isIdle()` (line 223: no pending, no turn, status `idle`); at claim time `thread/read` is asked again and `turn/start` starts the turn. A thread leaves when it drops out of `thread/loaded/list` (line 341). No code handles `thread/closed` itself; the next tick's loaded list does.
- Where a "person attached" check goes: in `attach()` before `thread/resume` (decide to join or not), in the `canReceive` callback (line 251) and again inside `deliver` after the `thread/read` at line 265 (a third place so a claim held for a while re-checks). The line-341 drop rule must stop dropping the thread when it is unjoined by design.

### 4. Options

| # | How it tells "a person's client is attached" | Cost | What can go wrong | Live check needed |
|---|---|---|---|---|
| 1 (recommended) | Receiver stays unjoined; thread listed in `thread/loaded/list` while we are not subscribed = some other connection is subscribed (or it left under 60 s ago). Status from `thread/read` (no join). Join at delivery, `thread/unsubscribe` when the turn ends | Rework of attach/idle logic in one file; one extra join and leave per delivery; no new call | 60 s window after the person quits (daemon setting `thread_unload_delay_secs`); any other subscriber counts as a person (second board page, an IDE or script client on the daemon); our own unsubscribe must run on every end path or the thread stays pinned and the check lies (a crashed page is safe: the daemon drops a dropped connection's subscriptions); two clients and an open idle TUI work (live); the desktop app or a client with `-c` options runs in-process, the thread is not on the daemon, so it is never loaded there and the board holds the message (the right outcome) | Done for the daemon and the TUI, no turn. Not done: the join-deliver-leave sequence with a real turn (needs a model turn) |
| 2 | Same signal but keep the receiver joined and ask another way: none exists (no subscriber list, no count) | n/a | Cannot be built | Not applicable (source and schema read) |
| 3 | Approval watchdog: while delivering, watch `thread/status/changed` for `active` with `waitingOnApproval`; if it lasts N seconds and no `serverRequest/resolved` came, call `turn/interrupt` and settle the message as `uncertain` | Small; works with the joined receiver too | After the fact: the approval has been shown to nobody for N s; a slow but present person gets the turn interrupted; the interrupt does not tell the card the person is away; tune N | Needs a model turn that asks for approval (earlier runs show the notices; the status flag itself was not read) |
| 4 | Send board turns with `approvalPolicy: "never"` (and no escalated sandbox) so no approval can wait | One field in `turn/start` | The override lasts "for this turn and subsequent turns", so the person's later turns in that thread change policy unless the receiver sets it back; commands that need approval now fail, so the board's work is weaker; touches the person's session settings, which the board has not done so far | Yes, with a model turn |
| 5 | Look at operating-system processes for `codex resume <id>` or the TUI's window | Platform code per OS | Fragile (the TUI is started in many ways), says nothing about the daemon, privacy-heavy | Not recommended |
| 6 | Ask the person to confirm on the board page ("I have Codex open") | A control | Not automatic; stale | No |

Option 1 plus Option 3 as a backstop covers the 60 s window. Option 4 is not recommended without the person's say.

## What a PR would change
- `scripts/codex-receiver.mjs`: `attach()` no longer joins; it records the thread and reads status with `thread/read`. A new helper `isPersonAttached(thread)` = "loaded now and not subscribed by this receiver" (use the same `loadedThreads(daemon)` result per tick, no extra call). `canReceive` and the loop at lines 260-277 also require it; if false the claim keeps waiting (the card then says to open Codex). `deliver` joins (`thread/resume`), starts the turn, and in the `finally` block calls `thread/unsubscribe` (handle `notLoaded` and a lost connection). The drop rule at line 341 and the `verify` at line 242 keep working, because an unjoined but loaded thread is in the list.
- `route()`: handle `thread/closed` for an attached thread (drop it at once, not on the next tick); the joined-only status notices stay for the delivery window.
- Board card text (`hooks/messaging.ts` or the page strings, where "Codex is waiting. It starts on this right away." lives): a "Open Codex to receive this" line for a thread that is held because nobody is attached.
- Tests (`tests/` receiver fixtures, with a fake daemon): (1) a loaded thread nobody else subscribes to (fake `thread/loaded/list` empty for it after its own unsubscribe) never gets `turn/start` and the message stays queued; it fails before the change, because today the receiver joins and starts the turn; (2) a thread that stays loaded while the receiver is unjoined starts a turn, then the receiver sends `thread/unsubscribe` after `turn/completed`; (3) `thread/closed` drops the attached thread at once; (4) the unsubscribe also runs on a refused `turn/start` and on a lost connection.
- Docs: `docs/MESSAGING.md` ("Why it is off by default") and a validation record for the new run.

## Not known
- The unexplained `thread/closed` 54 s before the client quit: most likely another thread, not proven. A check needs the receiver's log with thread ids (a run with a real turn, one more model turn).
- The join-deliver-unsubscribe sequence with a real model turn, including an approval during it (`waitingOnApproval` flag, `serverRequest/resolved`), and whether a `thread/unsubscribe` while a turn is still running is safe. Not run (zero turns).
- Whether the 60 s default can differ on a person's daemon (`thread_unload_delay_secs` in their config) and whether the Codex desktop app ever attaches to the shared daemon; only the TUI and raw clients were run.
- Linux and macOS; CLI/daemon versions other than 0.167.0/0.169.0 (the unload logic is recent; check `thread_unload_delay` exists before relying on it, and fall back to "not attached" when the daemon is older).
- A thread that is loaded because a hook, a goal or a background job keeps a subscriber (no case seen).
- Housekeeping: the test home's daemon and the pseudo-terminal clients were stopped; one saved session file was created in the test home by the raw clients (two empty threads) and left there; nothing else was changed.
