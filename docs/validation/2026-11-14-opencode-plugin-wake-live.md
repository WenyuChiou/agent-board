# Live check: the #1366 OpenCode plugin wakes an idle session from the board, and #1379's host questions

## Question
- #1366 (PM comment "What un-parks it", step 1): with the plugin generated by #1366's build, does a message sent from the board page wake an idle OpenCode session with nobody typing, and does the ACK come back to the card? What happens when a busy event arrives during the attempt? What does the plugin do against a board started from the previous release?
- #1379: what does OpenCode do with `promptAsync` on a session that is busy but has not announced it yet? Does the host keep a client-chosen `messageID`, must ids sort, what does a repeat with the same id do, and does `session.message` find one message by its id?

## Result
- A, idle wake from the board page: PASS. A message typed on the card woke the idle session within 1 s (queued to `promptAsync` accepted: 0.87 s), with nobody typing in OpenCode. The model called `agent_board_ack`, and the card read "Replied · Synthetic test A: PONG-A; no files changed."
- B, busy session: PASS for both shapes. B1: while a turn ran, the plugin took nothing (`queued`, card "OpenCode is working. It gets this when this step ends." / "Queued") and woke the session 0.67 s after `session.idle`. B2: the busy event that came during the attempt made the plugin release the message as unsent 220 ms after the mark, without calling `promptAsync`. It was delivered once, 0.87 s after the turn ended.
- C, against a 0.24.3 board: FAIL. The 0.24.3 card's own "Queue for OpenCode's next turn" queued the message, and the plugin took it. The 0.24.3 hub refused `attempt`, `release --unsent` and `open` with `UNKNOWN_FIELD`. The message stayed claimed and undelivered for 95 s, the card claimed "No reply confirmed. Check the original conversation." and nothing was logged. Once the #1366 page replaced the 0.24.3 one, the message was delivered and acknowledged once, within 4 s.
- D, host API: shown (above). In short: a second `promptAsync` before the busy event is accepted and folded into the running turn, which answers only the newest message. Client ids are kept, need only the `msg` prefix, and need not sort for a new message to be answered. A repeat with the same id appends text to the stored message and starts no turn. One message can be fetched by its id (200 or 404).

## What this means for #1366 step 2 and #1379
- #1366 step 1: A and B are recorded. C reproduces part A's P1 live, and reaches it with less than the review found. The 0.24.3 page's own card queues to OpenCode ("Queue for OpenCode's next turn"), so no authenticated adapter is needed.
- For step 2's older-board change, as seen against 0.24.3: `open` is refused with `UNKNOWN_FIELD` and claims nothing, so it shows an older hub before any take. A plain `release` is understood, but it answers `ok: true` even for a ref it does not hold, so from an older hub that answer does not prove the claim went back. The plugin's attempt-failed and release-failed path writes no hook error, so a stuck claim leaves no trace.
- #1379 item 1 (confirm by id): the host supports it. A client `messageID` with the `msg` prefix is kept, `GET /session/{s}/message/{id}` answers 200 or 404, and the 404 is the proof of absence. A 200 answer carries the message's parts, including its text, so a narrow read can use only the status code. Re-sending with the same id after a 200 adds text to that message and starts no turn, so a send-again needs a new id.
- #1379, busy but not announced: the host neither refuses nor starts a second turn. It stores the message and the running turn answers only the newest message, so a wake that lands just after a person's prompt may get no reply of its own and no ACK. Up to about 450 ms after a 204, `GET /session/status` still answers idle. In B2 the plugin's event counter caught the overlap, through the other prompt's `chat.message` or busy event arriving before its own `promptAsync`.
- Cost: 8 model turns (A 1, B 4, C 1, D 2), within the budget of 8. D's two repeats used none.
